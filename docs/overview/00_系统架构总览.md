# vLLM 系统架构总览

> 本文把整个 vLLM V1 引擎串成一张图：分层架构、核心组件职责、一个请求从 HTTP 到 GPU 再返回的完整时序、关键数据流与设计取舍。可作为阅读各模块源码前的"地图"。

---

## 1. vLLM 是什么

vLLM 是一个高吞吐、低延迟的 LLM 推理与服务引擎，核心能力：

- **PagedAttention**：把 KV cache 像操作系统虚拟内存一样分页管理，极大降低显存碎片、提升并发；
- **连续批处理（continuous batching）**：每个迭代步动态组 batch，请求级抢占/恢复；
- **V1 架构**：当前默认引擎，用独立进程跑调度与计算、ZMQ 通信、编译 + CUDA Graph 优化；
- **开箱即用的服务**：OpenAI 兼容 API（chat/completions/responses/realtime）、离线 `LLM` 类、池化模型（embedding/rerank）、多模态、投机解码、LoRA、量化、PD 分离、张量/流水/专家/数据并行。

## 2. 顶层模块地图

```
vllm/
├── entrypoints/        # 服务入口：OpenAI API Server、批处理、Ray、SageMaker、gRPC
├── v1/                 # V1 引擎核心（默认）
│   ├── engine/         # AsyncLLM、EngineCore、调度输出处理、detokenizer、ZMQ 客户端
│   ├── core/           # Scheduler、KV cache 管理、block 分配、结构化输出、采样
│   ├── worker/         # GPUWorker、ModelRunner、输入批、micro-batch
│   ├── executor/       # 多进程/多节点执行器（multiproc/ray/uniproc）
│   ├── attention/      # 注意力后端（FlashAttention/FlashInfer/Triton MLA…）
│   ├── spec_decode/    # 投机解码（EAGLE/Medusa/ngram…）
│   ├── kv_offload/     # KV cache 卸载（CPU/分层缓存）
│   ├── pool/           # 池化输出（embedding/late-interaction）
│   └── structured_output/  # 结构化输出（grammar/FSM）
├── model_executor/     # 模型层积木：Linear(并行)、Attention、Norm、RoPE、MoE、SSM、pooler

│   └── models/         # 290+ 模型架构实现
├── compilation/        # torch.compile 分段后端、Inductor pass、CUDA Graph 包装
├── distributed/        # TP/PP/EP/DP/CP 通信组、NCCL、KV/EC connector、EPLB
├── lora/               # LoRA 运行时热加载与批内适配
├── multimodal/         # 多模态输入处理、processor registry、encoder cache
├── quantization/       # 量化方法（FP8/GPTQ/AWQ/GGUF/Marlin…）
├── tracing/            # OpenTelemetry 分布式追踪
├── config/             # 全部配置（VllmConfig 及子配置）
├── csrc/ + kernels/    # 原生 CUDA/Triton 算子
├── platforms/          # 平台抽象（CUDA/ROCm/CPU/XPU/TPU…）
├── plugins/            # 第三方插件机制
└── utils/ logging_utils/ ...  # 通用工具、日志
```

依赖方向基本是：`entrypoints → v1.engine → v1.core / executor → worker → model_executor.models → layers / attention / distributed`。

## 3. 分层架构（运行时进程视图）

一次 `vllm serve` 默认会启动**多个进程**：

```
┌──────────────────────────────────────────────────────────────┐
│  API 进程（Uvicorn + FastAPI）                                 │
│  entrypoints/openai/*  →  AsyncLLM(v1/engine/async_llm.py)    │
│  · HTTP/WebSocket、鉴权、chat template、tool/grammar          │
│  · InputProcessor(请求→EngineCoreRequest)                     │
│  · OutputProcessor + IncrementalDetokenizer                   │
│  · output_handler 后台 Task                                   │
└───────────────┬──────────────────────────▲───────────────────┘
                │ ZMQ (EngineCoreRequest)  │ ZMQ (EngineCoreOutputs)
                ▼                          │
┌──────────────────────────────────────────────────────────────┐
│  EngineCore 进程（v1/engine/core.py，忙等循环）                │
│  · Scheduler（core/sched/scheduler.py）连续批处理调度          │
│  · KVCacheManager 分页分配/回收/抢占/前缀缓存                  │
│  · StructuredOutputManager 语法约束                           │
│  · ModelExecutor（executor/）                                 │
└───────────────┬──────────────────────────▲───────────────────┘
        collective_rpc / shared mem
                │                          │
┌───────────────▼──────────────────────────┴───────────────────┐
│  Worker 进程（每 GPU 一个，v1/worker/gpu_worker.py）           │
│  · GPUModelRunner：构造 GpuInputBatch、调用模型、采样           │
│  · 模型（model_executor/models）+ 编译/CUDA Graph             │
│  · Attention backend、KVCache blocks、LoRA、spec decode       │
└──────────────────────────────────────────────────────────────┘
```

- **API 进程**：CPU 密集（tokenize、模板、detokenize、SSE），用 asyncio，避免阻塞 GPU；
- **EngineCore 进程**：调度大脑，单线程忙等，尽量不做 GPU 计算；
- **Worker 进程**：每卡一个，持有模型权重和 KV cache，真正执行前向。

> 单进程/测试场景用 `InprocClient` 把 EngineCore 放进同进程；Ray 后端把 EngineCore/Worker 包成 actor。数据并行时会有多个 EngineCore（DP），API 进程按波次（wave）分发。

## 4. 核心组件职责

### 4.1 入口与门面

| 组件 | 文件 | 职责 |
|------|------|------|
| `api_server` | `entrypoints/openai/api_server.py` | FastAPI app 装配、中间件、路由、生命周期 |
| `OpenAIServing*` | `entrypoints/openai/*/serving.py` | 各端点业务逻辑，调 `engine_client` |
| **`AsyncLLM`** | `v1/engine/async_llm.py` | API 进程的引擎门面：组合 InputProcessor/OutputProcessor/EngineCoreClient，暴露 `generate/encode` |
| `EngineCoreClient` | `v1/engine/core_client.py` | ZMQ 客户端：`MPClient`/`AsyncMPClient`/`SyncMPClient`/`InprocClient`/`DP*` |

### 4.2 引擎核心

| 组件 | 文件 | 职责 |
|------|------|------|
| **`EngineCore`/`EngineCoreProc`** | `v1/engine/core.py` | 主循环：收请求 → `step()` → 发输出；DP/Ray 变体 |
| **`Scheduler`** | `v1/core/sched/scheduler.py` | 连续批处理：从 waiting 选请求进 running、抢占、调度策略（fcfs/priority）、chunked prefill |
| **`KVCacheManager`** | `v1/core/kv_cache_manager.py` | 物理 block 池、逻辑→物理映射、前缀缓存、滑动窗口、CP |
| `SchedulerOutput`/`CachedRequestData` | `v1/core/sched/` | 一步的调度结果、请求缓存状态 |
| **`ModelExecutor`** | `v1/executor/` | 对 Worker 的抽象：`Uniproc`/`Multiproc`/`Ray` 执行器，collective_rpc |

### 4.3 Worker 与模型

| 组件 | 文件 | 职责 |
|------|------|------|
| `GPUWorker` | `v1/worker/gpu_worker.py` | 加载模型、执行一次 `execute_model`、采样/池化、collective 通信 |
| **`GPUModelRunner`** | `v1/worker/gpu_model_runner.py` | 最复杂的组件之一：把调度结果拼成连续张量、准备 Attention metadata、跑前向、采样、写 KV、CUDA Graph 重放 |
| `GpuInputBatch` | `v1/worker/gpu_input_batch.py` | GPU 上的请求状态（软max、输入 id 等） |
| 模型 | `model_executor/models/*` | 网络结构，用 layers 积木搭建 |
| 层积木 | `model_executor/layers/*` | 并行 Linear、Attention、FusedMoE、RMSNorm、RoPE、Embedding… |
| Attention 后端 | `v1/attention/` | backend/impl/metadata，真正的 attention kernel |

### 4.4 横切能力

- **compilation/**：`@support_torch_compile` → `VllmBackend` 切图 → `PiecewiseBackend` 多形状编译 → `CUDAGraphWrapper` 捕获/重放；
- **distributed/**：`GroupCoordinator` 管理 TP/PP/EP/DP/CP 组；KV/EC connector 做 PD 分离；EPLB 做 MoE 专家负载均衡；
- **multimodal/**：`MultiModalRegistry`、processor、encoder cache；
- **lora/**：运行时 LoRA 热加载，批内按请求路由不同 adapter；
- **spec_decode/**：draft model/proposer + target model 校验（EAGLE/Medusa/ngram）；
- **structured_output/**：grammar/FSM 约束采样；
- **tracing/**：OTel 跨进程 trace 传播；
- **kv_offload/**：KV cache CPU 卸载与复用。

## 5. 一个生成请求的完整时序

以流式 `POST /v1/chat/completions` 为例，标注各阶段所在进程与关键调用。

### 阶段 A：API 进程 — 接收与预处理

```
HTTP 请求
  │ FastAPI 路由 → OpenAIServingChat.create_chat_completion
  │ ① 鉴权/CORS/请求 ID 中间件
  │ ② 校验 model、解析 messages/tools/response_format
  │ ③ render_chat_request：chat template 渲染 → EngineInput（token/embedding + 多模态）
  │ ④ request.to_sampling_params()：构造 SamplingParams（温度/top_p/max_tokens/stop/grammar/logprobs）
  ▼
AsyncLLM.generate(request_id, engine_input, sampling_params)
  │ ⑤ InputProcessor.process_inputs：
  │      - 校验参数/LoRA/长度
  │      - 应用 generation_config、tokenizer eos
  │      - 组装多模态 MultiModalFeatureSpec
  │      - 生成 EngineCoreRequest
  │ ⑥ RequestOutputCollector 建立（每请求异步队列）
  │ ⑦ engine_core.add_request_async(core_req) ── ZMQ ──▶ EngineCore
  │ ⑧ async for out in collector.get(): yield  # 等输出
  ▼
（端点把 RequestOutput 转成 ChatCompletionChunk，SSE 逐块发送）
```

### 阶段 B：EngineCore 进程 — 调度

```
EngineCoreProc.busy_loop
  │ ⑨ _process_input_queue：从 ZMQ 收 EngineCoreRequest
  │      → Scheduler.add_request（构造 CachedRequestData，进 waiting 队列）
  │
  │ ⑩ _process_engine_step → Scheduler.schedule()：
  │      - 从 running 选可继续 decode 的请求
  │      - 从 waiting 选可加入的 prefill（受 KV block 预算/最大 batch/最大 token 约束）
  │      - 显存不足时抢占（PREEMPTED→重新计算或换出）
  │      - 处理 prefix caching（命中的块直接复用）
  │      - 处理 chunked prefill（长 prompt 分多步）
  │      - 为新请求分配物理 block（KVCacheManager.allocate_slots）
  │      - 产出 SchedulerOutput（每请求的 block_table、num_computed_tokens、num_tokens 等）
  ▼
ModelExecutor.execute_model(SchedulerOutput) ──collective_rpc──▶ Worker
```

### 阶段 C：Worker 进程 — 执行

```
GPUWorker.execute_model / GPUModelRunner.execute_model
  │ ⑪ 把 SchedulerOutput 物化成 GPU 张量：
  │      - flatten 所有 token 到 input_ids[num_tokens]
  │      - 构造 positions、block_table、slot_mapping、seq_lens、query_start_loc
  │      - 准备 Attention metadata（按 backend 不同，含 P/D 分离、CP、滑动窗口）
  │      - 采样参数、LoRA 映射、结构化输出 bitmask、spec decode 校验
  │ ⑫ _prepare_inputs（可能走 CUDA Graph 输入填充）
  │ ⑬ 模型 forward（已编译/图捕获）：
  │      - Embedding → N × DecoderLayer（RMSNorm → Attention → MLP/MoE）→ Norm
  │      - Attention 层从 forward_context 取 metadata，读/写分页 KV cache
  │      - TP all-reduce/all-gather、MoE EP all-to-all
  │ ⑭ sampler 采样（argmax/top-k/top-p/beam/grammar 约束/投机校验）
  │ ⑮ 把新 token 的 KV 写入对应 slot（或由 backend 内部写）
  │ ⑯ 返回 SamplerOutput / PoolerOutput
  ◀── collective_rpc 返回
```

### 阶段 D：EngineCore — 后处理与回传

```
EngineCore.step 拿到 ModelRunnerOutput
  │ ⑰ Scheduler.update_from_output：
  │      - 把采样 token 追加到请求
  │      - 判断停止（eos/stop string/max_tokens/abort）→ FINISHED
  │      - 释放完成请求的 block（KVCacheManager.free）
  │      - 更新前缀缓存块
  │ ⑱ 构造 EngineCoreOutputs（每请求 new_token_ids、finish_reason、logprobs、stats、events）
  ▼
ZMQ send ──▶ API 进程
```

### 阶段 E：API 进程 — 输出处理与流式返回

```
AsyncLLM._run_output_handler（后台 asyncio Task）
  │ ⑲ engine_core.get_output_async()
  │ ⑳ OutputProcessor.process_outputs：
  │      - 按 request_id 找 RequestState
  │      - IncrementalDetokenizer.update(new_tokens)：增量解码 + stop string 检查 + Unicode 边界
  │      - logprobs 处理、prompt logprobs
  │      - 按 stream_interval 决定是否产出
  │      - 组装 RequestOutput（含 usage、finish_reason）
  │      - 请求结束时记录统计/tracing
  │ ㉑ collector.put(RequestOutput)
  ▼
generate 的 async for 拿到 RequestOutput
  │ ㉒ 端点转 OpenAI 响应：
  │      - 流式：delta content/reasoning/tool_calls，SSE 推 chunk
  │      - 非流式：累积后返回完整 ChatCompletionResponse
  ▼
HTTP 响应返回客户端
```

请求结束或客户端断开：`generate` 捕获 `CancelledError/GeneratorExit` → `engine_client.abort(request_id)` → EngineCore 下一步释放其 KV block。

## 6. 关键数据流

### 6.1 KV cache：分页机制（PagedAttention）

```
逻辑序列 seq_id
   └─ block_table: [逻辑块号] → 物理块号
物理块池 KVCacheManager.block_pool：
   └─ 固定大小的 GPU 张量 [num_blocks, num_kv_heads, block_size, head_dim]
       （及可选 CPU 卸载块、跨机 KV connector 块）
```

- 注意力算子通过 `block_table + slot_mapping` 间接访问 KV，物理块不必连续；
- 请求增长时按需分配块，结束即归还，几乎无外部碎片；
- **前缀缓存**：相同前缀的块通过 hash 共享（copy-on-write）；
- **抢占**：显存不足时把运行中请求的块换出/释放，之后重算或从卸载恢复；
- **CP/EP**：上下文并行切分块，专家并行影响调度但对 KV 透明；
- **kv_offload/KV connector**：把块放到 CPU/远端，PD 分离时在实例间传输。

### 6.2 控制流与数据流解耦

- **控制路径**：API → ZMQ → EngineCore（请求/中止/配置）是小消息；
- **数据路径**：KV/权重不经过 ZMQ，而是在 Worker 进程的 GPU 上，通过 NCCL/共享内通信；
- 这让 EngineCore 保持轻量，能高频率调度（默认每步几十~几百微秒级）。

### 6.3 批处理演进（continuous batching）

每一步 `Scheduler.schedule()` 重新决定这一步谁参与：
- 某个请求这一步 decode 1 个 token，另一个请求刚到在 prefill，第三个被抢占重算——它们可以在**同一个前向**里（拼接成 `num_tokens`）；
- `GpuInputBatch` 用软最大容量管理，避免频繁重建张量；
- chunked prefill 把长 prefill 拆成多步，与 decode 混跑以稳定延迟。

## 7. 模型前向的一次调用长什么样

以 LlamaDecoderLayer 为例（第 05 篇），在 Worker 进程内：

```python
# RMSNorm 融合 add + norm（返回 residual）
hidden_states, residual = self.input_layernorm(hidden_states, residual)
# QKV 投影（ColumnParallel，按 head/GQA 切）→ Attention
attn_out = self.self_attn(positions=positions, hidden_states=hidden_states)
# Attention 层从 forward_context 取 attn_metadata、kv_cache：
#   q/k/v → RoPE → 写 KV → attention kernel（按后端）→ o_proj
hidden_states, residual = self.post_attention_layernorm(attn_out, residual)
hidden_states = self.mlp(hidden_states)   # gate_up fused + SiluAndMul + down(RowParallel)
```

- 没有显式的"把哪些 token 放一起"逻辑——模型只看到拼好的 `[num_tokens, hidden]`；
- 批/序列边界信息全部在 `attn_metadata` 里，由 ModelRunner 构造、attention backend 消费；
- 张量并行的通信（all-reduce/gather）藏在并行 Linear 里；MoE 的 all-to-all 藏在 FusedMoE 里。

## 8. 编译与 CUDA Graph（性能支柱）

- 模型类用 `@support_torch_compile` 标记；
- `VllmBackend` 在 attention/MoE 等不透明算子处**切图**，每段用 Inductor 针对多个 token 数范围编译；
- `CUDAGraphWrapper` 按 `BatchDescriptor`（token 数、uniform decode、LoRA 组合）捕获并**重放整图/分段图**；
- `PIECEWISE` 图适合 prefill（形状多变），`FULL` 图适合 decode（固定形状），v1 默认 `FULL_AND_PIECEWISE`；
- Worker 在 `capture_model()` 阶段对所有 bucket 预热捕获，稳态执行几乎无 Python 开销。

这是 V1 高吞吐的关键之一。

## 9. 并行维度总览

第 08 篇详述，这里给一张速查：

| 并行 | 切什么 | 通信 | 组件 |
|------|--------|------|------|
| **TP** | 单层权重（列/行） | all-gather / all-reduce / reduce-scatter | `parallel_state._TP`、并行 Linear |
| **PP** | 模型层（按深度） | P2P send/recv `IntermediateTensors` | `_PP`、`make_layers` |
| **EP** | MoE 专家 | all-toall dispatch/combine | `_EP`、FusedMoE、all2all managers |
| **DP** | 复制模型/多引擎 | 波次同步 | 多 EngineCore、`DPAsyncMPClient` |
| **PCP/DCP** | 长上下文 KV/attention | KV halo 交换 | `_PCP/_DCP`、CP utils |
| **SP** | 序列维度切分 | all-gather/reduce-scatter | sequence parallelism |

进程 rank 布局为 `ExternalDP × DP × PP × PCP × TP`。

## 10. 多模态、LoRA、投机解码、池化的接入点

- **多模态**：prompt 中带占位符；InputProcessor 组装 `mm_features`；Worker 内 vision encoder（encoder-only attention）产出 embedding，按 `PlaceholderRange` 合并到 text embedding；encoder 输出可缓存（mm_hash）。
- **LoRA**：启动时静态加载或运行时热加载；ModelRunner 维护 `LoRAModelManager`，前向时按请求的 LoRA id 选择不同的低秩权重（批内多 adapter）。
- **投机解码**：draft 模型/ngram 先产出 K 个候选 token，target 模型一次前向校验，接受符合的前缀（spec_decode/）。
- **池化**：`AsyncLLM.encode` 而非 generate；Worker 末尾用 Pooler 聚合（LAST/AVG/CLS/late-interaction/分类头），返回 `PoolingRequestOutput`。
- **PD 分离**：prefill 端通过 KV connector 逐层 save KV，decode 端 load 并直接进入 decode（调度器侧 `get_num_new_matched_tokens`）。

## 11. 配置、日志、可观测性

- **`VllmConfig`**（config/）是贯穿所有组件的单一配置对象，分 Model/Cache/Parallel/Scheduler/Compilation/LoRA/Multimodal/... 子配置；
- **日志**（logging_utils/、entrypoints/logger.py）：统一格式、每请求日志、KV cache 用量、Prometheus 指标；
- **Tracing**（tracing/）：`@instrument` 埋点 + W3C `traceparent` 跨进程传播，导出到 OTel collector（见 [Tracing 系列](./tracing/)）；
- **指标**：`/metrics`（Prometheus）、每引擎统计、iteration stats。

## 13. 一张图记住全链路

```
Client ──HTTP──▶ FastAPI ──▶ AsyncLLM ──ZMQ──▶ EngineCore
                    ▲            │                 │
                    │            │ InputProc       │ Scheduler + KVCache
                    │            ▼                 ▼
                 SSE/JSON   OutputProcessor   ModelExecutor ──rpc──▶ GPUWorker
                    ▲            │                 │                     │
                    └────────────┴──ZMQ────────────┘              Model.forward
                                                          (Attention/KV/MoE/NCCL/CUDAGraph)
```
